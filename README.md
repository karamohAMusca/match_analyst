# Match Analyst AI ⚽

An assistant coach built with **`datapizza-ai v0.1.0`** (AITHO GenAI Academy final project).
The coach describes their own team and the opponent; the assistant helps prepare the match and handle
in-game situations, with advice **grounded in cited sources** (Coverciano theses, recent finals,
match data), giving priority to recent (2022–2026) winning tactics. Questions in Italian or English.

> **Status:** complete: knowledge base, hybrid retrieval, the agent with its corpus tools,
> input/output guardrails (the facts of a real match, coaches and teams, the side of a game
> situation, unsupported additions: 20 errors found and handled, see `eval/error_log.md`),
> conversation memory, tracing in Phoenix, the Streamlit app and the evaluation with an LLM judge.
> The knowledge base is also an MCP server, usable from Claude Desktop and other hosts. Final
> gold run (2026-10-21): faithfulness 0.958, relevancy 0.926, abstention 3/3, recall@5 0.95,
> p95 9.0 s, 0.0011 $ per answer ([results](#results-41-questions-answers-with-guardrails-on-judge-gpt-41-mini)).

## Getting started

Prerequisites: Python ≥ 3.10; Docker Desktop (for Qdrant); an OpenAI API key for ingestion and
the agent (not for tests and maintenance scripts).

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # then add OPENAI_API_KEY
```

### Offline checks (no API key, no network)

```bash
python -m pytest                   # corpus, retrieval, agent loop (fake model), guardrails, evaluation, app, MCP server
python -m pytest --cov=src --cov=scripts --cov-report=term-missing   # which lines the tests never run
python -m scripts.check_corpus     # quotes and cited pages vs references/ (needs the PDFs in references/theses)
```

Coverage is read, not just accepted: the core (retrieval, tools, guardrails, judge, gold run) is
at 96–100%; what stays uncovered is the code that talks to Qdrant, OpenAI or Phoenix, checked by
running the project. Line coverage does not test the limits, so the thresholds (question length,
follow-up words, advice words) have tests on the exact value.

### Maintaining the corpus

After adding or editing a card, regenerate the manifest and re-run the tests:

```bash
python -m scripts.build_manifest
python -m pytest
```

Writing rules for cards are in [`references/SOURCES.md`](references/SOURCES.md).
The manifest stores the SHA-256 of each card's bytes, so line endings matter: `.gitattributes` makes
git check out every text file with LF line endings, also on Windows (with CRLF, a clone would see
every card as changed, in the tests and in the ingestion).

### Building the index (Qdrant + OpenAI embeddings)

Each card is split into one chunk per `##` section (about 110 chunks); the front matter is stored
as payload, not embedded. The sync is incremental: only new or changed cards are embedded again.

```bash
docker compose up -d                       # start Qdrant on localhost:6337
python -m scripts.ingest --dry-run         # preview chunks and cost (no key, no Qdrant)
python -m scripts.ingest                   # embed and store the cards (about $0.0003)
python -m scripts.ingest --query "Come si attacca un 4-4-2 basso?"   # retrieval check
```

`python -m scripts.ingest --reset` rebuilds the collection from scratch.
Qdrant dashboard: http://localhost:6337/dashboard

### Measuring retrieval on the gold set

```bash
python -m scripts.eval_retrieval
```

Retrieval is hybrid: dense search (Qdrant) + BM25 keyword search, fused into one ranking, at most
1 chunk per card. The script compares dense, BM25 and hybrid variants on recall@1, recall@5 and
MRR@10 (the standard definitions), also by question type and language; each run is saved in `eval/runs/`.
Question vectors are cached in `.cache/`: the first run embeds them in one call (well under
$0.001), later runs are free, and `python -m scripts.eval_retrieval --offline` needs no API key.

### The app (uses the OpenAI API)

```bash
python -m scripts.start           # Qdrant + Phoenix (Docker), wait until ready, then the app
                                  # (log live in the terminal; Ctrl+C: review of the session's chats)
python -m scripts.start --stop    # stop Qdrant and Phoenix (index and traces are kept)
streamlit run app.py              # only the app, if the services are already running
```

The app opens at http://localhost:8501.

Three tabs. **Chat**: the conversation with the assistant coach (follow-up questions work);
citations appear as badges with the card title, the cards of the answer can be read in full next
to it; when the coach writes the formations ("noi giochiamo 4-3-3, loro un 4-4-2 basso"), the answer
shows them on a pitch, drawn in the app's colours with the players running to their place (an
indicative layout, read from the question, not a fact of the cards); when the answer cites a final
as its real case, its timeline follows (goals and score, saves, red cards, changes, extra time and
penalties, each from the card's own words) and, for the two finals with StatsBomb event data (2022
World Cup, Euro 2024), the action of a goal: the ball travelling through the passes at the real tempo,
every player named when he touches it; and every answer shows what the guardrails did and, under "Dettagli", its time, tokens,
cost and the searches the agent made. The sidebar starts a new conversation, switches model and
guardrails (to show them at work) and has example questions, one in English and one off topic.
**Schede**: the 31 cards by category. **Valutazione**: the measured results of the saved runs
(no API call). With Phoenix running, every question is also a trace.

### Saved chats and the log

Every conversation of the app is saved in `chats/`, one JSON Lines file per chat named after the
time it started (`2026-09-30_153012.jsonl`), one line per answer written as soon as it is given:
question, answer, consulted cards, searches, guardrails, time/tokens/cost, and the turns added to
the agent's memory (datapizza `Memory`, tool calls and results included). The sidebar button
"⬇️ Scarica la chat" downloads the current one.

```bash
python -m scripts.review_chats            # the last chat, answer by answer (offline, no key)
python -m scripts.review_chats --all      # every saved chat
```

It runs the automatic checks of `eval_agent` on every saved answer, against the text of the cards
it consulted: citations only to consulted cards, names and numbers present in those cards or in
the coach's questions, tool use, answer language. An answer built on cards read earlier in the
same chat is checked against those cards, and a "Non lo so" is not flagged for citing nothing.
Each answer shows its tokens: in a long chat they grow turn after turn, because the conversation
memory keeps the cards read before (from about 1,700 to 54,000 tokens in a 15-question chat). Then
the chat's totals (flagged answers, questions stopped, rewrites, time, tokens, cost).

What happens while chatting (app and CLI) is written to `logs/match_analyst.log`: new
conversation and its file, every question (its length, not its text), the input guard's verdict,
the searches with the cards found and their time, the output guard and the rewrite, every answer
with time, tokens and cost; warnings for stopped questions and discarded rewrites; errors with
their stack trace. `LOG_LEVEL=DEBUG` in `.env` also writes the search queries. The file is rotated
at 1 MB (5 old files kept). Both folders are git-ignored: they hold what the users typed.

With `python -m scripts.start` everything is in one terminal: while the app is open the log lines
are printed there too (marked `[log]`), and Ctrl+C closes the app and prints the review of the
chats of that session (the same report as `scripts.review_chats`) with where the chats and the log
are.

### Chat with the agent from the terminal (uses the OpenAI API)

The agent (gpt-4o-mini) searches the cards with its tools (`search_cards`, `read_card`), answers
only from the passages it retrieved, cites every claim with its `[document_id]`, and says
"Non lo so" when the cards do not cover the question. Needs Qdrant running and the index built.

```bash
python interactive_cli.py                                   # conversation, follow-ups work
python interactive_cli.py "Come preparo una partita contro un 4-4-2 basso?"   # one question
```

After each answer the CLI lists the cards the agent consulted and, when they intervened, what the
guardrails did.

**Guardrails** (`src/guardrails/`, code that prevents instead of a prompt that asks):
- *input*: prompt-injection attempts, off-topic and oversized questions get a fixed reply and
  never reach the model; greetings get the presentation without a model call (a greeting followed by
  a football question is a football question, E14);
- *output*: the answer must be in the language of the question, its names and numbers must appear
  in the consulted cards (in an English answer, the Title Case words of headings and bold labels are
  not names, E16; their numbers are still checked), and it must cite `[card_id]`s it actually consulted. On a problem the
  model gets a precise note and rewrites the answer once; the rewrite is kept only if it is not
  worse, and what happened is always reported;
- *real case* (`src/guardrails/real_case.py` and the other modules of `facts.py`, no model call): the real match of an advice answer is where
  roles got swapped ("Inter defended a lead in the 2023 final", "Leverkusen's man-to-man press"),
  with every name in the cards. The model now writes only `Caso reale: [case_id]`, and the code writes
  the facts with the card's own sentence on that final (the line of a consulted game-situation card
  that cites it, else the match card's outcome), so its roles cannot be swapped. A line about
  something else (a match of a thesis, a season of a coach) that cites a consulted card stays as
  written and is checked like any sentence; a final no consulted card speaks of is removed.
  **Coach-team pairs** ("the Atalanta of Italiano", "PSG was coached by Scaloni") must be in the cards
  (the team in the coach's card, or the pair of a final), and **thresholds** about a metric ("PPDA
  below 10") must be written in them. **The side** of a game situation: if the coach says "we are down
  to ten" (or behind, or ahead), the card written for the other side (playing 11 v 10, defending a
  lead, coming back) may only describe the opponent's moves, never be the coach's own advice (E17).
  With **a man down**, which has no card, and no score given, the answer is written by code: "Non lo so" for the advice,
  the options of the 11 v 10 card as what the opponent will try (its own words, with a note that
  there "the opponent" is the coach's team), and a real case from the side that was down to ten
  (Argentina in the 2026 final), with no model call. A **score the coach never gave** ("keep your
  lead" when no score was mentioned) is not taken for granted (E6).
  A wrong fact goes into the single rewrite; if it is still there, the sentence is removed. On every saved answer of the real runs (766), the facts flagged are exactly
  the known errors (E3, E4, E5).
  A **closing summary** with no citation ("Queste regole aiutano a mantenere l'equilibrio", "In
  sintesi..."), the most frequent unsupported statement of the reference gold run, is removed: it
  carries no cited fact (a style question's conclusion, "X is the closest to your team", is kept).
  An English question reaches the model with a one-line reminder to answer in English: with the
  rule of the system prompt alone, every English answer was drafted in Italian and rewritten.
  A name the cards write only in part ("Philipp Lahm", "Bayern Monaco") is cut back to their words
  by code, before the checks: asked to the rewrite, the whole name went, Lahm included (E9). A detail
  said to be missing without the words "Non lo so" ("un allenatore non specificato") gets them (E19).
  An **effect added after a comma** ("..., creando opportunità di tiro", "..., evidenziando un pressing
  molto efficace"), the writer's reading and not the card's, is cut (E20); a tail with a number or a
  name stays. Simulated on the judge's verdicts of two gold runs, it raised faithfulness by 0.011 and
  0.019, no required fact lost; it also cuts some right tails, so answers get shorter.
- *verifier*, optional (`src/guardrails/verifier.py`, a second model after the writer: a sequential
  architecture): the checks above see names, numbers and citations, not who did what ("Inter
  defended a lead" passes them, while the card says City won). The verifier runs the gold run's
  claim-by-claim check at answer time, writing who does what to whom in each statement and in its
  evidence before deciding; each unsupported statement goes into the same single rewrite, with what
  the cards say. **Off by default** (`--verifier` in `eval_agent` and `gold_run`): measured on the
  gold set it raised faithfulness from 0.923 to 0.949, under the +0.03 the acceptance gate requires,
  for 5 times the cost (0.0064 $ per answer) and 4 times the latency (p95 32 s). On the known
  errors it works (it catches the swapped roles of E2 and the invented threshold of E5), but a
  single check is not stable: in one run it quoted the right sentence and called the wrong one
  supported (see `eval/error_log.md`).

To check answers automatically on a set of gold questions (citations only to consulted cards,
grounding, language, correct tool use, "Non lo so" when required, required facts; ~$0.02 for
the default 8 questions):

```bash
python -m scripts.eval_agent            # or --ids Q13,Q18, or --all
python -m scripts.eval_agent --all --no-guardrails     # bare agent, to measure the guardrails
python -m scripts.eval_agent --all --model gpt-4.1-mini   # another model
python -m scripts.eval_agent --follow-up                  # two turns: conversation memory
```

`--follow-up` measures the conversation memory: a follow-up question of the gold set ("E se invece
ci pressano alti a uomo?") is asked right after its previous turn ("...noi giochiamo 4-3-3, come
la prepariamo?") in the same conversation; besides the usual checks, the expected card must be
consulted and the answer must use the previous turn.
Result (run `agent_20260929-112013`): the memory works, the follow-up is understood and the expected
card is found. The prompt now tailors the advice to what the coach wrote about their own team, so
the first turn builds on "your 4-3-3". **Known limit:** in the second turn, facing a new situation,
the model reasons about that situation and does not always bring back the coach's formation.

### Use it from Claude Desktop and other MCP hosts

`mcp_server.py` gives the knowledge base to any MCP host: Claude Desktop, Claude Code, VS Code +
Copilot (Agent mode), Cursor, the MCP Inspector, or Python code with `mcp.Client`. The host's own
model reads the cards; the app's agent is not involved, so the measured results of this README do
not change. It is built with the reference MCP SDK (`mcp` ≥ 2, spec 2026-07-28, stateless):
datapizza-ai 0.1.0 has no MCP server, and its MCP client speaks only the older protocol.

| Primitive | Name | What it does | Needs |
|---|---|---|---|
| tool | `search_cards(query, categories)` | the agent's hybrid search: up to 5 cards, each headed by its `[document_id]` | Qdrant; the key for a new query |
| tool | `read_card(document_id)` | one whole card | nothing |
| tool | `list_cards(category)` | the catalogue: id, title, category and date of each card | nothing |
| resource | `card://{document_id}` | one card by URI; the 31 cards are listed | nothing |
| prompt | `prepare_match(team, opponent)` | the recipe: search game situations and real matches, cite every sentence, "Non lo so" when the cards do not cover it | nothing |

The tools are read-only (they declare it to the host) and look cards up by id, never by path.
Catalogue and cards are read from `corpus/`, the same text the agent reads, so they work with
nothing running. `search_cards` needs Qdrant (`docker compose up -d`) and reads the key from the
project's `.env`: no key goes into a host's configuration. A server started before Qdrant works as
soon as Qdrant is up. The log goes to `logs/match_analyst.log`, and with Phoenix running every
search is also a trace.

A host starts the server itself, with absolute paths. Below, `<PYTHON>` is the Python of the
environment where `requirements.txt` is installed (with the setup of
[Getting started](#getting-started): `<PROJECT>\.venv\Scripts\python.exe` on Windows,
`<PROJECT>/.venv/bin/python` on macOS and Linux) and `<PROJECT>` is the absolute path of this folder.

- **Claude Desktop**: Settings → Developer → Edit Config, add the server to
  `claude_desktop_config.json`, then restart Claude Desktop. In JSON, Windows paths take double
  backslashes (`C:\\Users\\...`) or forward slashes.
  ```json
  {
    "mcpServers": {
      "match-analyst": {
        "command": "<PYTHON>",
        "args": ["<PROJECT>/mcp_server.py"]
      }
    }
  }
  ```
- **Claude Code**: `claude mcp add match-analyst -- <PYTHON> <PROJECT>/mcp_server.py`
- **VS Code + Copilot**: in `.vscode/mcp.json`,
  `{"servers": {"match-analyst": {"type": "stdio", "command": "<PYTHON>", "args": ["<PROJECT>/mcp_server.py"]}}}`,
  then Copilot Chat in Agent mode. **Cursor**: `.cursor/mcp.json` with the same block as Claude Desktop.
- **MCP Inspector** (needs Node.js), to try the tools by hand:
  `npx @modelcontextprotocol/inspector <PYTHON> <PROJECT>/mcp_server.py`
- **Over HTTP** (Streamable HTTP, stateless): `MCP_HTTP=1 python mcp_server.py` (PowerShell:
  `$env:MCP_HTTP=1; python mcp_server.py`), then connect to `http://localhost:8000/mcp`.

### Gold run: the whole system judged by an LLM

```bash
python -m scripts.gold_run --tag baseline              # ~$0.2 with gpt-4o-mini
python -m scripts.gold_run --tag gpt41 --model gpt-4.1-mini
python -m scripts.gold_run --tag verifier-on --verifier      # with the verifier (off by default)
python -m scripts.gold_run --rejudge eval/runs/agent_20260928-180737.json --judge-model gpt-4.1-mini
```

The same gold set, one table of metrics: recall@1, recall@5 and MRR of the first expected card,
faithfulness and relevancy given by an LLM judge with typed outputs, abstention on out-of-corpus
questions, latency p50/p95, cost per query and of the run, and one score,
(faithfulness + relevancy) / 2. Faithfulness is judged claim by claim, as in RAGAS: the answer is
split into statements, each is checked against the cards the agent consulted, and the score is
the share of supported statements; the statements that are not supported are listed. (A single
score per answer, `--faithfulness holistic`, gave 1.0 to answers we know are wrong.) The detail
marks the questions below 0.7, and a reminder maps each low metric to what to try. Off-topic, greeting and follow-up questions test the
guardrails and the conversation and stay in `eval_agent`. With Phoenix running, the run is one
trace, `gold_run <tag>`, with every question inside. Runs are saved as `eval/runs/gold_<time>.json`.
`--rejudge` judges the saved answers of an earlier run again (on the cards that run consulted), to
compare judges on exactly the same answers: a judge is trusted only if it catches the answers we
know are wrong. The default judge is gpt-4.1-mini; a judge error is left out of the averages and
counted. Every run is listed in [`eval/runs/README.md`](eval/runs/README.md).
The judge's verdicts are saved in `.cache/`: its client gets a disk cache with datapizza's `Cache`
interface (`src/core/disk_cache.py`), and datapizza looks every call up there before asking the
model. Judging the same answer again with the same judge costs nothing, so a `--rejudge` stopped
halfway starts again without paying what it already judged; the "judge cost" line says how many
calls the cache answered, and `--no-judge-cache` asks the judge again (e.g. to see how much its
verdicts vary). The clients of the agent and of the judge are built by datapizza's `ClientFactory`.

#### Results (41 questions, answers with guardrails on, judge gpt-4.1-mini)

| Agent model | Faithfulness | Relevancy | Score | Abstention out of corpus | Trap Q18 (thesis attributed to a later team) |
|---|---|---|---|---|---|
| **gpt-4o-mini** (default) | 0.910 | 0.934 | 0.922 | 2/3 | 0.78 |
| gpt-4.1-mini | 0.914 | 0.980 | 0.947 | 2/3 | 0.00 |

Retrieval on the same questions: recall@1 0.76, recall@5 0.95, MRR 0.84. Live run with gpt-4o-mini:
latency p50 5.0 s / p95 10.1 s, about 0.0012 $ per answer. gpt-4o-mini is the default: the same
faithfulness at about a third of the cost, and no wrong attribution on the trap question;
gpt-4.1-mini gives more complete answers and can be chosen in the app.

**Final run** (live run `gold_20261021-111545`, gpt-4o-mini with guardrails, after the fixes of the
errors in `eval/error_log.md`) against the reference of 2026-10-09 (`gold_20261009-112356`, before
them), same judge, same agent model:

| Metric | Reference 2026-10-09 | Final 2026-10-21 | Rule of acceptance |
|---|---|---|---|
| faithfulness | 0.923 | **0.958** (+0.035) | at least +0.03 and at least 0.85: passes |
| relevancy | 0.974 | 0.926 (−0.047) | lower, see below |
| abstention out of corpus | 3/3 | 3/3 | — |
| recall@5 / MRR | 0.95 / 0.84 | 0.95 / 0.84 | at most −0.02: passes (retrieval untouched) |
| latency p50 / p95 | 4.1 s / 7.2 s | 4.8 s / 9.0 s | p95 about 10 s: passes |
| cost per answer | 0.0012 $ | 0.0011 $ | within budget |

The runs in between (`-141635`, `-143834`, `-145440`, `eval/runs/README.md`) show the gain step by
step: 0.944, 0.946, 0.953, 0.958. The first of them also showed what a fix can break: the abstention
fell to 2/3 until a missing detail said without "Non lo so" got the words by code (E19).
With the verifier (`-114805`, before these fixes): faithfulness 0.949, relevancy 0.966, p95 32.3 s,
0.0064 $ per answer, so it stays off by default.

**What the numbers do not say.** The gold set holds few of the errors found in the app (the real
case, the side of a game situation, the greeting, the premise): they are checked by tests on the
saved answers and in the app, not by this table. Faithfulness moved by +0.035 while 20 errors were
fixed. The relevancy fell because of a few right answers marked down, not because answers got
worse: Q35 asks for a PPDA threshold that the cards do not give and the answer says "Non lo so"
(the reference answered with an invented threshold and had 1.0), Q07 and Q32 leave a half
unanswered or do not name the source. Known limits, in the error log: a source conflict left out
(E7), questions on two cards answered with one (E8), a role taken from the question (E15), and the
relevancy judge, which rewards an answer that sounds complete.

**Choosing the judge**, on answers whose errors are known (runs `gold_20260929-094225`, `-094857`,
`-101624`):

| Judge | Catches the known errors (Q18, Q12, Q35) | False alarms on correct answers | Cost of one full judgement |
|---|---|---|---|
| gpt-4o-mini, one score per answer | 0 of 3 (1.0 to every answer) | — | ≈ 0.03 $ |
| gpt-4o-mini, claim by claim | at most 1 of 3, not stable between runs | several | ≈ 0.05 $ |
| **gpt-4.1-mini**, claim by claim | 2 of 3 (misses the invented threshold of Q35) | few | ≈ 0.13 $ |
| gpt-4.1, claim by claim | 3 of 3 | fewest | ≈ 0.75 $ |

gpt-4.1 is the best judge but costs about six times more: routine runs use gpt-4.1-mini, and its
limits are known. Two more limits of the judge: an omission (a source conflict left out, Q17) is
not seen statement by statement, and it is covered by the required-facts check of `eval_agent`;
gpt-4.1-mini judging its own answers may favour them slightly, which would only overrate the model
we did not choose. A judge from another provider (`--judge-provider`, e.g. `anthropic`) would
remove that doubt: not tried, it needs that provider's datapizza client package and its key in `.env`.

### Tracing with Phoenix

`docker compose up -d` also starts [Arize Phoenix](http://localhost:6006). With Phoenix running,
the CLI and `eval_agent` turn every question into one trace: input guardrail, each agent step,
the searches with the chunks found (card id and score), every model call with its messages and
tokens, the output guardrail and the rewrite with the cards it was given. datapizza-ai emits
OpenTelemetry spans with its own attribute names; `src/observability/tracing.py` translates them
to the OpenInference names Phoenix reads. If Phoenix is not running, tracing is switched off and
the scripts say so; `eval_agent --no-trace` switches it off on purpose.
